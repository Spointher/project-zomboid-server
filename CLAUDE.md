# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the canonical guide for the repo; the points below are the highest-signal items for working in it.

## Repository Shape

- This repo packages a Project Zomboid dedicated-server container. There is no package manifest, test suite, linter, formatter, or CI in this checkout — do not invent `npm`/`make`/`pytest` flows.
- `server/` is the Docker build context. `server/Dockerfile` copies `start.sh` and `Server/` using paths relative to `server/`, so builds must be invoked with `server` as the context.
- `server/Server/` holds a **generic `server.*` profile template**, not a deployment's live config. The real profile stem comes from `SERVER_NAME`; on first boot `start.sh` derives `${SERVER_NAME}.ini`, `${SERVER_NAME}_SandboxVars.lua`, `${SERVER_NAME}_spawnpoints.lua` and `${SERVER_NAME}_spawnregions.lua` from the template, and never touches a profile that already exists.
- The image puts that template at `/home/pzuser/profile-template`, **outside** `/home/pzuser/Zomboid`. That is deliberate: `Zomboid` is a named volume and Docker only seeds a volume that is still empty, so a template copied into it would be invisible on any volume that already exists. Do not move it back under `Zomboid/Server`.
- The compose file is `server/docker-compose.yml` — there is no `compose.yaml`.

## Commands

- Build image (from repo root): `docker build -f server/Dockerfile server`
- Launch via compose (from `server/`): `cp .env.example .env`, set at least `ADMIN_PASSWORD`, `CODE_SERVER_PASSWORD` and `RCON_PASSWORD` (compose fails without them), then `docker compose up -d --build`
- Shell syntax checks: `bash -n server/start.sh`, `bash -n server/vm-hardening.sh` and `bash -n upload_to_server.sh`
- Harden the VM (once, on the VM, as root): `sudo bash vm-hardening.sh` — preview with `bash vm-hardening.sh --dry-run`
- Admin console: `docker exec -it project-zomboid-server pz-rcon players` (also `save`, `servermsg "..."`, `quit`)
- **After deploying, the VM needs `docker compose up -d --build`, not `up -d`.** `start.sh` is `COPY`ed into the image (`server/Dockerfile:56`), so the container runs `/start.sh` from the image, *not* the copy `upload_to_server.sh` just wrote into the deploy directory. Without `--build` the old script keeps running while the new one sits on disk looking deployed. `start.sh` logs `revision: /start.sh <mtime> sha <12>` at boot — compare it against `sha256sum server/start.sh`, or run `docker exec project-zomboid-server wc -l /start.sh`. (Diagnostic trick: the line number bash cites in `/start.sh: line N: … Killed` is the `wait "$pz_pid"` line, which differs between revisions.) Compose/`.env` changes do apply with a plain `up -d`.
- Deploy to VM: `./upload_to_server.sh` (use `--dry-run` first to list files that would be uploaded). It tars local `server/` contents into `/home/homelab-admin/project-zomboid-server` on `homelab-admin@games-server.homelab.net` over SSH. **`.env` is gitignored and does not travel in the tar** — remote env changes are manual.

## Runtime Architecture

- Base image is **`debian:12-slim`**. SteamCMD comes from Valve's tarball (`$STEAMCMD_PATH`), not from apt — the Debian repos have no usable `steamcmd` package.
- **`pzuser` is pinned to uid/gid 1001 via `ARG PZ_UID`/`PZ_GID` — do not remove the pin.** The old `ubuntu:24.04` base already shipped an `ubuntu` user at uid 1000, so `pzuser` landed on 1001 and every file in the existing `zomboid-data` / `pzserver-install` volumes is owned by 1001. `debian-slim` has no such user, so a plain `useradd` gives 1000 and the container loses write access to its own world.
- **The game is not baked into the image.** The build only installs SteamCMD; `start.sh` installs app `380870` (~7 GB) at boot into the `pzserver-install` volume. This is what keeps the image at ~400-500 MB instead of ~8 GB. Reproducibility comes from the version pin (below) rather than from image contents.
- `procps` is required in `debian-slim` for the compose healthcheck's `pgrep` — Ubuntu shipped it implicitly, Debian does not. Do not drop it.
- **Do not install a JRE.** PZ bundles its own at `/opt/pzserver/jre64` and `start-server.sh` uses it; `default-jre` added ~200 MB for nothing. If the launcher ever fails to find Java, export `JAVA_HOME=/opt/pzserver/jre64` in `start.sh` instead.
- **The game version is `PZ_BRANCH` + `PZ_AUTO_UPDATE` in `.env`, and the pin is on disk, not on the branch.** `PZ_BRANCH` maps to SteamCMD's `-beta` and is currently **empty = the public branch** (Build 42.20.2, buildid `24574884`). It is not `42.19` any more: TIS never published a frozen `42.20` branch, and a client refuses to join a server on a different build, so tracking `public` is the only way to be on the current stable. Named branches (`42.19` = Build 42.19.1 buildid `24438606`, `legacy41` = Build 41.78.20) are still frozen and still valid values. List branches with `curl -s https://api.steamcmd.net/v1/info/380870 | jq '.data["380870"].depots.branches'`.
- Because `public` moves on its own, `start.sh` records the installed branch in **`/opt/pzserver/.pz-installed-branch`** (inside the `pzserver-install` volume) and `needs_install` skips SteamCMD entirely when the marker matches `PZ_BRANCH` and `PZ_AUTO_UPDATE` is falsey. `.env.example` ships `PZ_AUTO_UPDATE=false`, so a restart cannot bump the server past clients that have not updated. Setting `PZ_AUTO_UPDATE=true` for one boot takes the update; changing `PZ_BRANCH` forces a reinstall regardless of the flag. Note the compose default is `true` (preserves the old always-update behaviour for an `.env` that omits the key) while `.env.example` ships `false` — that asymmetry is intentional.
- **`.env` is gitignored and is not in `upload_to_server.sh`'s tar, so version changes have to be applied to the VM's `.env` by hand** — the deployed version can silently drift from `.env.example`.
- **`download_depot` does not work here — do not reintroduce `PZ_MANIFEST_*`.** Pinning an exact build outside a named branch was tried and fails: an anonymous Steam account is licensed for app `380870` (so `app_update` works) but not for its depots, and Steam answers `Depot download failed : missing license for depot (No subscription)`. `start.sh` then exits and `restart: unless-stopped` turns it into a restart loop. Making it work would require credentials for an account that owns the game.
- `install_via_app_update` distinguishes config errors from transient ones: on `Failed to set beta` / `No subscription` / `missing license` it prints a `FATAL:` line and stops retrying, because retrying a bad `PZ_BRANCH` under `restart: unless-stopped` is a silent loop.
- SteamCMD is flaky on a cold cache (`Failed to install app '380870' (Missing configuration)`). `start.sh` retries `app_update` 3 times and deletes `steamapps/appmanifest_380870.acf` between attempts — do not collapse that loop.
- `server/start.sh` runs as container entrypoint: optionally starts `code-server` on `0.0.0.0:8443` (auth via `CODE_SERVER_PASSWORD`), installs/updates PZ, seeds the profile, patches the JVM flags in `ProjectZomboid64.json` (PZ ignores `-Xmx` passed on the command line), writes identity keys into the profile `.ini`, then runs `start-server.sh`.
- **code-server is off by default** (`ENABLE_CODE_SERVER`, default `false`). It shares the game container's cgroup, so its ~300-500 MB come out of the same `mem_limit`. `CODE_SERVER_PASSWORD` stays `:?`-required in compose even when it is disabled, so enabling it can never leave `:8443` unauthenticated.
- **`-Xms` is deliberately NOT `-Xmx`.** `start.sh` patches `-Xmx` to `PZ_HEAP` and `-Xms` to `PZ_HEAP_MIN` (default `512m`). They used to be equal, which made the JVM commit the whole heap in the first second of boot — concurrently with everything else starting — and that is the moment the 6 GB VM locked up. It also patches `-XX:MaxMetaspaceSize=256m`, `-XX:MaxDirectMemorySize=512m`, `-XX:ActiveProcessorCount` (floored from `PZ_CPUS`; the JVM otherwise sizes its GC/JIT pools against the host's CPU count and ignores compose's `cpus:` quota) and `-XX:+ExitOnOutOfMemoryError` (without it a heap OOM leaves a live-but-useless JVM that the `pgrep` healthcheck still reports healthy). Valueless flags need `add_jvm_flag_once`, not `set_jvm_flag` — the latter's replace branch would eat what follows and its `+` is a regex metacharacter.
- **PZ runs in the background on purpose — do not add an `exec`.** `start.sh` traps `TERM`/`INT` and sends `quit` over RCON, which is the ordered shutdown (warn → save → exit). `wait` returns as soon as the trap fires, so the `tail --pid=$pz_pid -f /dev/null` at the end is what actually holds the container open until the save completes. Removing it truncates the world write. `stop_grace_period` is 90s; a stop that takes exactly 90s means SIGKILL, i.e. the trap did not work.
- `server/docker-compose.yml` persists `/home/pzuser/Zomboid` and `/opt/pzserver` in named volumes. Deleting either wipes saved world/config or the installed server respectively.
- **The healthcheck needs the bracket trick: `pgrep -f '[P]rojectZomboid64'`.** Plain `pgrep -f ProjectZomboid64` matches the healthcheck's own `sh -c` process, so it returns 0 forever — the container reported `healthy` (with PIDs in the output) while PZ was dead in a restart loop.
- Memory/CPU: `PZ_HEAP` (default `2g`) is **only** the JVM heap; `PZ_MEM_LIMIT` (default `3584m`) and `PZ_MEMSWAP_LIMIT` (default `4608m`) are the container's `mem_limit`/`memswap_limit`, and `PZ_CPUS` (default `3`) is `cpus`. Defaults are sized for the 6 GB / 4 vCPU `games-server` VM.
- **The sizing rule has THREE conditions, not one.** Getting the second wrong is what made the VM freeze on every PZ start:
  1. `PZ_MEM_LIMIT ≈ PZ_HEAP + 1.5 GB` — the container's own overhead (JVM non-heap, PZ native, code-server).
  2. `PZ_MEM_LIMIT ≤ VM RAM − 2 GB` — the host's reserve.
  3. `PZ_CPUS ≤ nproc − 1` — so `sshd` always has a core.

  The two reserves are **different numbers on purpose** (`CONTAINER_OVERHEAD_B` 1.5 GiB vs `HOST_RESERVE_B` 2 GiB in `start.sh`). Set them equal and `4608m` on a 6144m VM lands exactly on the boundary and passes — i.e. the rule keeps blessing the config that froze the machine. The page cache PZ streams its map through is charged to the host side.
- **"At most the VM's RAM" was the old rule 2 and it is not a safety margin.** `4608m` on a 6144m VM passed every check while leaving the host ~1.5 GB for kernel + systemd + dockerd + sshd + page cache. PZ mmaps ~2 GB of assets and map chunks through that budget; with `memswap_limit == mem_limit` **and** no swap on the VM, the kernel had nowhere to evict anonymous pages, so it never reached a clean OOM and livelocked reclaiming instead — the whole VM hung, SSH included, with nothing in the logs. A `mem_limit` above physical RAM is still worse (the cgroup never fills at all), but staying under it is not enough.
- **`memswap_limit` is now ~1 GB ABOVE `mem_limit`, reversing the old "equal on purpose" setting.** The old rationale was "fail fast rather than thrash"; it did not fail fast, it hung the host. A container that spills a gigabyte to disk is slow, a VM you cannot SSH into is down.
- `report_memory_budget` in `start.sh` logs `heap / container limit / host RAM / host swap` plus `PZ_CPUS / nproc` at boot, and warns on all three rules **plus a host with zero swap** — that last condition is what turns an overshoot into a frozen VM and used to be entirely invisible. It only warns: exiting would be a restart loop under `restart: unless-stopped`, and clamping silently would hide the misconfiguration. `start.sh` also reads `ProjectZomboid64.json` back after patching and warns if `PZ_HEAP`/`PZ_HEAP_MIN` did not land.
- **The container limits are only half the fix — the VM needs `server/vm-hardening.sh` run once as root.** It adds a swapfile (which is what makes `PZ_MEMSWAP_LIMIT > PZ_MEM_LIMIT` mean anything), `vm.min_free_kbytes=131072` (the reclaim reserve that prevents the livelock), `vm.swappiness=10`, `earlyoom` configured to prefer `java` and avoid `sshd`/`dockerd`, `OOMScoreAdjust=-900` on the ssh unit, and persistent journald — without which a hard reboot erases the evidence, which is why no freeze so far left any. It is idempotent and has `--dry-run`. Note `earlyoom`'s regexes in `/etc/default/earlyoom` must stay **unquoted**: systemd splits `$EARLYOOM_ARGS` on whitespace without stripping quotes afterwards.
- RCON `27015/tcp` is intentionally **not** published. The image ships gorcon's `rcon` plus `server/pz-rcon`, a wrapper that fills in the container address and password.
- **Never generate a script inside a `RUN`.** Docker does not unescape `\$` the way you would expect — the backslashes survive into the file and bash then reads `"\$"` as a literal `$`, so nothing expands. A `printf`-generated `pz-rcon` broke exactly this way (`address ${ip%% *}:${RCON_PORT:-27015}: too many colons`). Ship scripts as files in the build context and `COPY --chmod=0755` them.
- **`start.sh` must export `LD_LIBRARY_PATH` with `${PZ_PATH}/jre64/lib` and `/lib/server` before launching.** PZ's `start-server.sh` points it at `jre64/lib/amd64` (the old JDK8 layout, absent from the bundled JRE), so its `LD_PRELOAD` of `libjsig.so` fails with `cannot be preloaded`. `libjsig` is the JVM's signal-chaining library — the SIGTERM fallback in `shutdown_pz` depends on it. Do not patch `start-server.sh`: SteamCMD overwrites it on every `app_update`.
- **`UPnP` is forced to `false` at boot** via `set_ini_key`, not only in the template, so it also reaches volumes that already exist. In a container it is useless (compose publishes the ports) and PZ warns it can hang the boot.
- Build and first run depend on network reachability to: Debian apt mirrors, `code-server.dev`, GitHub (rcon-cli release), SteamCMD, and Steam app `380870`.

## Config Gotchas

- `SERVER_NAME` selects the profile **and the saved-world directory** (`Saves/Multiplayer/${SERVER_NAME}`). Changing it on a live server makes PZ start a new empty world. The `games-server` VM runs `SERVER_NAME=teampapo`; that line must exist in its `.env`.
- Identity keys (`RCONPassword`, `Password`, `PublicName`, `PublicDescription`, `RCONPort`) are injected at boot from env via `set_ini_key`, which **only writes when the env value is non-empty**. That is deliberate: an unset variable leaves the volume's existing value alone.
- The server runs **vanilla Build 42** — `Mods=` and `WorkshopItems=` are deliberately empty in the template. If mods come back, update both keys and keep them in sync.
- `/home/pzuser/Zomboid` is a named volume, so editing the template in the repo does **not** reach a server whose volume already exists. Either edit in-volume through code-server on `:8443`, or `docker compose down -v` (which wipes the world).
- Build 41 saves cannot be loaded by a Build 42 server; there is no converter.
- There are **four separate passwords**, and only one of them is meant to be shared. Do not collapse them again:

  | Variable | Used by | Shared with |
  |---|---|---|
  | `CODE_SERVER_PASSWORD` | code-server auth on `:8443` (`export PASSWORD=`) | nobody |
  | `ADMIN_PASSWORD` | the in-game `admin` account (`-adminpassword`) | nobody |
  | `SERVER_PASSWORD` | the `.ini` `Password=` key — what players type to join | the players |
  | `RCON_PASSWORD` | remote console, and the ordered shutdown | nobody |

  `CODE_SERVER_PASSWORD` and `ADMIN_PASSWORD` are both `:?`-required in compose and re-checked in `start.sh`. `:8443` is published without TLS, which is why the IDE login is not the admin secret.
- `SERVER_PASSWORD` is written through `set_ini_key`, which no-ops on an empty value — so once a join password reaches the volume, **blanking the env var does not remove it**; edit `Password=` in the `.ini` instead.
